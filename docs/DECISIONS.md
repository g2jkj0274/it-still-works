## 2026-09-06 — 시드 RNG 싱글턴의 이름은 `sim/sim_rng.gd` (class `SimRng`)
- 결정: 헌법·`builder.md`가 말하는 `sim/rng.gd`는 기존 `sim/sim_rng.gd`를 가리킨다. 파일을 옮기거나 이름을 바꾸지 않는다.
- 근거: 감사(docs/AUDIT.md) 결과 이 파일은 P3를 그대로 만족하고(`get_state/set_state`로 해시·청크 저장 대응) 테스트가 붙어 있다. 이름 하나 맞추자고 이력을 끊을 이유가 없다.
- 버린 대안: `sim/rng.gd`로 rename — 옛 참조(legacy)와 uid 캐시가 어긋난다.

## 2026-09-06 — legacy/ 는 참조하지 않는다. 꺼낼 때는 복사한다
- 결정: `legacy/`(`.gdignore`)의 파일을 `load()`·`preload()`·`class_name`으로 참조하지 않는다. 재활용은 파일을 복사해 `sim/`·`view/`로 가져오고 헌법에 맞게 고친 뒤 테스트를 붙이는 것이다.
- 근거: `.gdignore` 아래는 Godot 파일시스템 스캔에서 빠져 전역 클래스로 등록되지 않는다. 참조하면 어느 날 조용히 깨진다.
- 버린 대안: legacy를 별도 브랜치/태그로만 두기 — 다음 마일스톤에서 꺼낼 때 diff 보기가 불편하다. `.gdignore` 확인이 실패하면 이 대안으로 간다(AUDIT "legacy/ 이동 방법 3").

## 2026-09-06 — M0 legacy 이동은 한 커밋 크기 제한(파일 5개·300줄)의 예외
- 결정: legacy 이동 + 골격 잘라내기는 한 커밋으로 간다(파일 300개 이상).
- 근거: 나누면 그 사이 트리가 파싱조차 안 되는 상태로 커밋된다. "테스트 통과 시에만 커밋"(LOOP 1.5)이 더 상위 규칙이다.
- 버린 대안: 디렉터리별로 나눠 커밋 — 중간 커밋마다 테스트가 깨진다.

## 2026-09-06 — `.gdignore` 로 legacy/ 를 빌드에서 뺀다 (확인됨)
- 결정: `legacy/.gdignore` 하나로 legacy 전체를 Godot 스캔·임포트·전역 클래스 등록에서 제외한다. AUDIT "이동 방법 3" 의 대안(`.gd.txt` 개명, 별도 브랜치)은 쓰지 않는다.
- 근거: `.godot/` 삭제 → `--import` → `--quit` 절차에서 "hides a global script class" · Parse Error · SCRIPT ERROR 0건. `global_script_class_cache.cfg` 에 legacy 경로 0건, 등록 클래스 12개 전부 새 골격. legacy 의 중복 `class_name`(SimRng 등)이 충돌하지 않았다.
- 버린 대안: 위 둘. 필요 없어졌다.

## 2026-09-06 — 창발 테스트는 M3 부터
- 결정: LOOP 1.6 의 마일스톤 종료 창발 테스트는 부품이 있는 M3~M6 에서만 수행한다. M0~M2 는 완료 조건만으로 닫는다.
- 근거: 창발 테스트는 "부품 조합으로 비의도 기계"를 요구하는데 M0~M2 에는 부품이 없다. LOOP 3.2 의 "12개 이상(마일스톤당 3개)"도 M3~M6 네 마일스톤 × 3 = 12 로 정확히 맞는다.
- 버린 대안: M1/M2 에서 블록·중력만으로 창발 테스트 — 부품 없는 조합은 스킬의 통과 기준(몹 규칙 1개 이상)을 만족할 수 없다.

## 2026-09-06 — 블록 레지스트리는 상태가 아니라 규칙이다
- 결정: `data/blocks.json` → `BlockRegistry` 의 내용은 상태 해시에 넣지 않는다. 대신 `digest()`(속성 열 순서·이름·값에서 만든 SimHash)를 저장 파일에 적고, 불러올 때 다르면 거부한다(M1-10).
- 근거: 표는 코드와 같은 층이다. 표 값이 바뀌어 동작이 바뀌면 상태가 갈려 골든 해시가 어차피 깨지고, 동작이 안 바뀌면 골든이 그대로인 것이 맞다. "같은 시드 + 같은 입력 = 같은 상태"에 "같은 빌드"가 암묵 전제인 것과 같다.
- 버린 대안: 해시에 포함 — 열 하나 늘 때마다 GOLDEN_HASH 가 바뀌어 회귀 테스트 신호가 흐려진다.

## 2026-09-06 — 블록 id 0 은 빈 칸, 내구도 0 은 부술 수 없음
- 결정: (a) 블록 id 0 = `air`. `PackedByteArray` 를 0 으로 채우면 빈 청크다(M1-2 전제). (b) `durability` 정수 하나로 P2 의 `breakable(내구도)` 를 나타낸다 — `0` = 부술 수 없음, `>0` = 부술 수 있고 그 값이 최대 내구도. 별도 `breakable` 불리언은 없다. (c) `BlockRegistry.max_durability(id)` 는 초기값이다. 개별 블록의 현재 내구도는 청크 상태(P7 보존 대상)에 산다.
- 근거: 헌법 P2 원문이 `breakable(내구도)` 로 하나의 속성이다. 채집(M1-7)과 몹 파괴(P10)는 `is_breakable` 만 물으면 된다. `solid` 로 물으면 안 된다 — legacy `is_carryable` 이 그 실수를 했다.
- 버린 대안: `breakable` 불리언 + `durability` 정수 둘 — 서로 어긋날 수 있는 두 필드.

## 2026-09-06 — 세계는 층 3개의 2D 격자다. 높이 축은 없다
- 결정: 세계 = `LAYER_UNDER=0`(지하) · `LAYER_GROUND=1`(지상) · `LAYER_UPPER=2`(2층) 세 층이 쌓인 2D 격자. 한 층의 한 칸에 블록 하나. 복셀 높이 축은 없다. 회로는 층 안의 2D 격자 위에 놓이고(P8), 아이소메트릭은 한 층을 한 화면에 그린다.
- 파생(미리 이름 붙여 둔다 — 안 적으면 M3/M6 에서 높이 축을 몰래 다시 들이게 된다):
  - 바닥 = 아래 층의 solid 칸. 지하층 아래는 암묵 기반암(M1-6 이동 규칙).
  - `gravity`·액체의 "낙하" = 아래 층 칸이 air 일 때 층 사이 이동(M3/M6). 같은 층 안에서는 떨어지지 않는다.
  - 층 사이 신호 전달은 P8 3항대로 별도 부품이며 M4 이후.
- 근거: P8 원문 세 줄이 모두 이쪽이다 — "회로는 2D 그리드 위에", "수직 복잡도는 층 전환으로 푼다"(층이 대체물이지 슬라이스가 아니다), "층 사이 신호 전달 부품은 M4 이후"(복셀 기둥이면 전선을 위로 이으면 될 일이라 부품이 필요 없다).
- 버린 대안: 복셀 기둥 + 층은 화면 슬라이스 — P8 3항과 충돌하고, legacy 가 그 길로 갔다(64×64×24).

## 2026-09-06 — 청크 16×16 × 층 3, 셀당 바이트 둘(id · 현재 내구도)
- 결정: `CHUNK_SIZE=16`, `LAYERS=3`, 셀 768. 셀 인덱스 = `(layer*16 + y)*16 + x`. 저장은 `_ids: PackedByteArray` + `_durability: PackedByteArray`(현재 내구도 0..255). 따라서 `blocks.json` 의 `durability` 는 255 이하(레지스트리가 검증).
- 정규형(P3): `id == 0`(air) 이면 durability 는 반드시 0. `set_id(..., 0, d)` 는 d 를 버리고 0, air 칸 `set_durability` 는 거부. 0..255 밖 값은 거부(클램프·랩어라운드 금지 — PackedByteArray 대입은 256 이 0 으로 조용히 접힌다).
- dirty 계약(P7): `empty()`·`from_bytes()` 직후 clean. 값이 실제로 바뀔 때만 dirty. 범위 밖 set 은 dirty 아님. dirty 는 digest 에 안 들어간다. 언로드 저장은 dirty 청크만 적는다 — `set_durability` 가 dirty 를 놓치면 내구도가 조용히 유실된다(P7 2항이 지키라는 바로 그 값).
- 근거: 셀당 바이트는 인덱스가 고정이라 정규형이 구조에서 나온다. "깎인 셀만 목록" 은 정렬·정규화에 딕셔너리와 레지스트리 지식이 필요해 P3 위반 지점이 생기고 같은 세계가 두 표현을 갖는다. 청크당 768B 추가는 반경 3 에서도 37KB.
- 성능 메모: 5ms/1000부품 예산은 부품 목록 순회 비용이지 셀 수 비용이 아니다. M3 중력·M6 액체를 "로드된 전체 셀 스캔"으로 짜면 반경 2 에서 19,200셀/틱 — 그때 architect 검토에 "활성 셀 목록(정렬된 PackedInt32Array)" 조건을 건다. 32 는 dirty 단위가 4배, 8 은 청크 간 조회가 는다 — 16 유지.
- 버린 대안: 위 목록 방식, 복셀 그리드(legacy).

## 2026-09-07 — 지형 표 `data/terrain.json` 은 레지스트리와 같은 층의 규칙이다
- 결정: 생성기가 놓을 블록 id 는 `data/terrain.json`(`TerrainTable`)에서 온다. 키는 역할 이름만(`under_zones`, `ground_zones`, `ground_scatter`) — 블록 이름이 스키마에 새지 않는다. 표는 상태 해시에 넣지 않고 `TerrainTable.digest()` 를 저장 파일에 적어 M1-10 에서 대조한다. 골든 지형 해시(seed 20250901, 청크 (0,0), `test_chunk_generator.gd`)는 지형 규칙·표가 바뀌면 바뀐다 — 그것이 의도된 신호다. 바뀌면 이유를 여기에 적고 갱신한다.
- 근거: 레지스트리 결정(2026-09-06)과 같다. 표는 코드와 같은 층이라 상태가 아니다. 표 값이 바뀌면 세계가 바뀌므로 저장 파일이 그 표를 기억해야 한다.
- 버린 대안: 표 내용을 상태 해시에 포함 — 골든 해시가 표 편집마다 바뀌어 회귀 신호가 흐려진다.

## 2026-09-07 — 생성기는 블록 정체를 모른다. 생성은 (seed, wx, wy) 의 순수 해시다
- 결정: (a) `ChunkGenerator` 안에 `ID_STONE` 같은 블록 id 상수를 두지 않는다. 놓을 후보 id 는 표에서 오고, 표는 로드 시 레지스트리 속성으로 검증된다(`under_zones`·`ground_scatter` 후보는 `solid` 여야 함, `ground_zones` 는 air 또는 solid). 검증이 `id < count()` 뿐이면 `blocks.json` 행 순서가 바뀔 때 지형이 조용히 바뀐다. (b) 생성은 `(world_seed, wx, wy, salt)` 정수 해시(splitmix64 계열, 64비트 랩어라운드)의 순수 함수다. 월드 `SimRng` 도 `RandomNumberGenerator` 도 쓰지 않는다. (c) 셀 값은 그 셀의 해시와 굵은 격자(`wx >> 3`) 해시만의 함수다. 이웃 셀에 찍는(stamping) 방식은 금지 — 청크 경계에서 이음새가 생긴다. (d) 정수 함정: 밀도 판정은 `h & 255`(`% 256` 은 음수에서 음수), 격자는 `>> 3`(`/ 8` 은 0 근처에서 폭이 15), 믹싱은 0 아닌 상수 덧셈부터 시작(시드 0·(0,0) 퇴화 방지). (e) JSON 파싱과 실수→정수 변환은 `TerrainTable` 에만 있다. 생성기 파일에는 실수·파일 IO 가 없고 테스트가 이를 grep 으로 지킨다.
- 근거: P2 — sim 코드가 블록 정체를 알면 속성 기반이 아니다. P7 — 월드 RNG 를 쓰면 청크 방문 순서(플레이어 경로)에 따라 지형이 달라진다. "같은 시드 = 같은 세계"는 경로와 무관해야 한다.
- 버린 대안: 생성기 안 id 상수(P2 위반); 월드 RNG 로 청크 생성(P7 위반); 렌더링·사운드처럼 P2 예외로 취급 — 생성은 상태를 만드는 sim 의 일이므로 예외가 아니다.

## 2026-09-07 — 로드 반경 `ChunkWorld.LOAD_RADIUS = 2` (25 청크)
- 결정: P7 이 말하는 "로드 반경 상수 하나" 는 `sim/chunk_world.gd` 의 `LOAD_RADIUS := 2`. 로드 중심 청크 기준 체비쇼프 거리 ≤ 2 → 5×5 = 25 청크(6,400 셀 × 층 3). 청크 좌표 변환은 `ChunkWorld.chunk_of(w)`(`>> 4`)·`local_of(w)`(`& 15`) 둘만 쓴다 — 산술 시프트·마스크라 음수 안전하고, 분산 재구현이 청크 경계 버그의 온상이므로 한 곳에 둔다.
- 근거: 화면 한 층이 한 청크 안팎이라 반경 2 면 화면 밖 두 청크까지 시뮬레이션이 산다. 첫 로드 25청크 약 45ms, 경계 넘기(변) 5청크 약 9.5ms, 모서리 9청크 약 17ms — 50ms 틱 안이다.
- 버린 대안: 반경 3(49청크, 첫 로드 약 90ms)·반경 1(9청크, 화면 밖이 바로 멈춤).

## 2026-09-07 — 언로드 스냅샷은 로드 시 소비하고 persist 표지로 대신 기억한다
- 결정: 한 키는 `_loaded` 와 `_snapshots` 중 정확히 하나에만 있다(불변식, 테스트로 지킨다). 로드 시 스냅샷이 있으면 그 바이트로 청크를 만들고 스냅샷을 지우고 `_persist[key]` 표지를 켠다. 언로드 시 `dirty or persist` 이면 스냅샷에 쓰고, 아니면 버린다(생성값과 같으니 다시 만들면 된다). dirty 와 persist 는 표지라 해시에 들어가지 않는다. **이 규칙 덕에 "변경 후 A 경로로 왕복" 과 "제자리에서 같은 변경만" 의 해시가 같다(P7 투명성).**
- 인정한 한계: 스냅샷에서 로드된 청크를 다시 생성값과 똑같이 되돌려도 언로드 시 스냅샷이 남아 순수 경로와 해시가 갈린다. 생성값과 대조(청크당 약 1.9ms)하지 않는 대가이고 결정론(같은 입력 = 같은 상태)은 유지되므로 허용.
- 버린 대안: 스냅샷을 지우지 않고 로드 뒤에도 보관 — 진실이 둘이 되고, 해시에 로드 이력이 새며(같은 내용인데 경로에 따라 다른 해시), 메모리가 이력만큼 는다.

## 2026-09-07 — 청크 생성은 즉시. 틱당 상한·대기열은 두지 않는다
- 결정: `set_center` 는 반경 안 청크를 그 자리에서 전부 생성한다. 대기열·틱당 상한 없음. `set_center` 는 명령으로만 `step()` 안에서 호출된다(M1-4b).
- 근거: 경계 넘기 최대 약 17ms 는 50ms 틱 안이고, 5ms/1000부품 예산은 부품 순회 기준이라 별개. 대기열은 "안 로드된 칸 set = false" 가 몇 틱 동안 명령 실패로 바뀌어 입력의 의미가 시간에 묶이는 새 결정론 위험을 들인다.
- 재검토 문턱: 한 번의 경계 넘기 > 25ms, 또는 생성기 규칙 추가로 청크당 > 4ms. 재검토 시 조건: 대기열 진행은 반드시 `step()` 안에서 틱당 고정 개수. `_process`·`delta` 금지.
